= Designer quickstart: preview a corridor guard

One command runs the whole chain: the IDApTIK corridor runner twice, then
Enaction's validator, then the explain lens. UMS links neither program; it
runs them as processes and reads the files they write (ADR-0019).

== 1. Build the three pieces

Each one is the owning repository's documented build. *All of them were
run on 2026-11-14*, exactly as written, at enaction-engine `d74a140`,
evil-weevil `c655f46` and IDApTIK `22797e0`, with Zig 0.16.0. The kernel's
own tests passed there (`zig build test`: 43/43). The zig command writes
`libevil_weevil.a` to `src/interface/ffi/zig-out/lib`, which is where
IDApTIK's `build.rs` looks under `EVIL_WEEVIL_ROOT`.

Since then the kernel's `main` carries ABI 1.2 (evil-weevil #11, `0560b09`,
"it models you"), and IDApTIK's runner needs it from `462af7c` on: a 1.1
kernel does not export `ee_model_fingerprint`, and the runner will not link.
The commands below fetch the three commits that `real-chain.yml` pins:
enaction-engine `11bd247`, evil-weevil `bffcbe3` (ABI 1.2) and IDApTIK
`9a89fcb`. These speak Enaction kernel contract 2.0: IDApTIK emits
`enaction-runner-output/2` and the validator accepts only that. Do not mix
them with older commits: enaction-engine `11bd247` refuses every document
from an IDApTIK before `9a89fcb` (such as `802b009`), which emits `/1`. Move
these commits only together with the pins in `real-chain.yml` and
`vendor/idaptik/PROVENANCE.json`.

[source,bash]
----
mkdir -p ~/weevil && cd ~/weevil
fetch() {
  git init -q "$1" &&
  git -C "$1" fetch -q --depth 1 "https://github.com/catachresis-colloquium/$1" "$2" &&
  git -C "$1" checkout -q FETCH_HEAD
}
fetch enaction-engine 11bd247b81dd336a5c153e588d99528002b321f3
fetch evil-weevil     bffcbe35e2258408e1adb52d097303807cdb3c26
fetch IDApTIK         9a89fcb0d7dc0d3f2080918def0dbcd4c1d04bf8

# The validator.
(cd enaction-engine && cargo build --locked -p enaction-contracts --bin enaction-validate)

# The Evil Weevil kernel, with Zig 0.16.0.
python3 -m pip install --no-cache-dir --target "$HOME/zig16" ziglang==0.16.0
export PATH="$HOME/zig16/ziglang:$PATH"
(cd evil-weevil && zig build --build-file src/interface/ffi/build.zig)

# The corridor runner.
(cd IDApTIK && EVIL_WEEVIL_ROOT="$HOME/weevil/evil-weevil" \
  cargo build --locked -p idaptik-weevil --bin idaptik-weevil-replay)
----

Then, in this repository:

[source,bash]
----
cargo build --locked -p ums-profile-sdk --bin ums-profile
export ENACTION_VALIDATE="$HOME/weevil/enaction-engine/target/debug/enaction-validate"
export IDAPTIK_WEEVIL_REPLAY="$HOME/weevil/IDApTIK/target/debug/idaptik-weevil-replay"
----

== 2. Preview the decoy

[source,bash]
----
target/debug/ums-profile preview \
  --runner "$IDAPTIK_WEEVIL_REPLAY" \
  --validator "$ENACTION_VALIDATE" \
  --policies vendor/idaptik/enaction-policies.json \
  --runner-output-flag --emit-epistemic \
  --runner-arg --profile --runner-arg decoy-lure \
  --runner-arg --ticks --runner-arg 200 \
  --runner-arg --seed --runner-arg 7 \
  --explain
----

What the flags do:

* `--runner-output-flag --emit-epistemic` makes the runner write its
  `enaction-runner-output/2` document (kernel contract 2.0) to a file that
  UMS chooses. For a scenario with a mind (`the-grudge`, `the-flinch`,
  `the-stalker`, `caught`, `false-exposure` and their controls), add
  `--mind-trace-flag --emit-mind-trace`;
* the runner runs twice, into two private directories. If the two documents
  differ by one byte, the preview stops with `ReplayMismatch`;
* `--policies` is your profile's `enaction-policies/1` file. Enaction takes
  the policies from you, never from the runner. The slice 2 scenarios
  (`the-stalker`, `caught`, `false-exposure` and their controls) hold
  models, beliefs about another agent's beliefs, so they need
  `vendor/idaptik/enaction-policies-models.json` (`depth.max_order` 1);
  under the depth-0 file the validator refuses them as `nesting-bounded`;
* if the validator refuses, the preview stops with `ValidatorRefused` and
  names the validator's rule and field path, for example `digest-matches at
  package.manifest.digest` for a document edited after it was sealed.

A real run first prints `replay-identical: ok` and `validator: accepted
(exit 0)`, and the report's inputs line ends `(validator-accepted)`.

How to read it: the decoy led the guard to suspect `contact-200` in room 0
on 36 ticks. World truth lists every stated proposition that is true, and
none of these is in it, so every belief diverges from the world: the decoy
worked. The cautious sentry, on the same corridor, has 36 beliefs and every
one agrees (`cautious-sentry.report.golden.txt`).

The line `models: 0; stale-divergent: 0; refused: 0` counts models. A
model is one agent's belief about another agent's belief. The decoy run
holds none. In the slice 2 scenarios the guard models what the contact
knows about where the guard is; the report shows each model's timeline
against the contact's own belief, never against the world, and marks a
model that was right when stated and later went wrong as
`stale-divergent`. `docs/ENACTION-ADAPTER.adoc` ("Models") explains the
rule; `false-exposure.report.golden.txt` is the example.

For a scenario with a mind, the report also has tick windows: the affect
token and what caused it to change, the ranking of candidates (never a
score), the incumbent commitment and the selected candidate. A tick where
the guard keeps its incumbent although the ranking prefers something else is
marked `commitment-override`. From `the-grudge.report.golden.txt`:

[source,text]
----
agent guard-0: commitment-override ticks: 37 of 200 (20..56) [tested]
  tells at: fixate@10..56; hesitate@57..59; startle@20, 56
----

The leak verdict is always `unverified (no counterfactual seam)`. The lens
cannot yet say that a guard did not learn something it should not know.

== Checks you can run without the binaries

[source,bash]
----
cargo test --locked -p ums-profile-sdk --test process_preview \
  --test explain_golden --test vendored_enaction --test vendored_idaptik \
  --test vendored_tom
----

With the binaries built, the full chain is an ignored test. It fails, rather
than passes, if either variable is unset:

[source,bash]
----
ENACTION_VALIDATE=... IDAPTIK_WEEVIL_REPLAY=... \
  cargo test --locked -p ums-profile-sdk --test real_chain -- --ignored --nocapture
----

On 2026-11-14 all 5 tests passed against binaries built by section 1, both
debug and release. One of them,
`the_grudge_cli_preview_matches_its_golden_report`, runs the designer
command for "the grudge" and requires its output to equal
`tests/fixtures/weevil-corridor/the-grudge.report.golden.txt`, apart from
the two header lines and the validation state. It reports 37
commitment-override ticks (20..56). Since 2026-11-19 CI runs these tests too:
`.github/workflows/real-chain.yml` builds the three binaries at pinned commits on every
relevant pull request and push, and at the siblings' latest commits once a week.

The file now holds 8 tests: three more for the slice 2 model scenarios
(#113). The coordinator reports that all 8 passed on 2026-11-15 against the
real runner at IDApTIK `462af7c` on the 1.2 kernel and the real validator.
That run is the coordinator's record; it was not repeated for this page.

== Shortcut: `just preview-weevil`

With `ENACTION_VALIDATE` and `IDAPTIK_WEEVIL_REPLAY` exported, one recipe
runs the whole preview for a scenario (default `the-grudge`, 200 ticks,
seed 7):

[source,bash]
----
just preview-weevil                 # the grudge
just preview-weevil the-flinch      # any mind scenario
just preview-weevil decoy-lure 200 7
----

It adds the mind-trace flags only for the mind scenarios, and passes the
depth-1 policies for the six slice 2 scenarios (`just preview-weevil
false-exposure`). It fails with exit 1 when either variable is unset, and
with exit 2 for an unknown scenario. All four behaviours were run on
2026-11-14 with just 1.59.0, before the slice 2 scenarios were added; those
were checked only with `bash -n` and an unset-variable run of the recipe
body, because just was not installed.
