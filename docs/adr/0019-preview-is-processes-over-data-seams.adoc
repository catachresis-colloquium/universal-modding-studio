= ADR-0019: Preview is processes over data seams

Date: 2026-11-14

== Status

Accepted (owner ruling, 2026-11-19), together with the 2026-11-14
amendment below. Proposed from 2026-11-14 until then.

Implements Enaction completion-plan step 19 and the replay rule of step 21,
as retargeted by `WEEVIL-HOST-ROUTE.adoc` (package A4).

== Context

ADR-0010 keeps Enaction behind an optional adapter, and ADR-0016 forbids UMS
in any shipped game's dependency graph. `SimulationAdapter` existed only as a
trait with a test implementation, so "deterministic preview" was designed and
not run.

A preview needs code from two other parties: the game's headless runner and
Enaction's validator. Linking either as a library would weld UMS to a game or
to the AGPL kernel, and would let one party read another's memory. The
Weevil route also requires that a closed engine can take part without linking
AGPL code, which only works if every seam is a process or a versioned
document.

== Decision

`ProcessPreviewAdapter` (`crates/ums-profile-sdk/src/preview.rs`) is the first
non-test `SimulationAdapter`. It:

. takes explicit paths to a runner binary and a validator binary. A bare
  command name is refused (`NotExplicitPath`), because it would be resolved
  through `PATH`. A missing file is `MissingBinary` and a non-executable one is
  `NotExecutable`. There is no fallback and no stub outside tests;
. launches each process with an argument array (no shell), a cleared
  environment, a per-process timeout and a stdout cap;
. runs the runner twice, as two separate processes, with the same input, and
  refuses with `ReplayMismatch` unless both stdout byte strings are
  identical. Replay identity is therefore checked inside every preview, not
  only in a separate gate;
. passes the runner's stdout to the validator on stdin. Exit 0 accepts.
  Exit 1 is `ValidatorRefused`, carrying the validator's rule name and field
  path. Any other exit is `ValidatorFailed`, so a broken invocation is never
  reported as a bad document;
. returns a response document described by
  `adapters/enaction/preview-response.schema.json`.

`ums-profile preview --runner PATH --validator PATH [--runner-arg ...]
[--validator-arg ...] [--explain]` is the command-line form.

UMS gains no Cargo dependency on Enaction or on any game. The adapter adds no
dependency at all: it uses the standard library, `serde_json` and `clap`,
which the crate already had.

== Consequences

* A designer's preview is replay-checked by construction, and a
  nondeterministic runner is refused, never averaged or retried.
* The validator, not UMS, is the authority on the documents. UMS checks only
  what it must to read them: UTF-8, one JSON document per line, integers
  within +-(2^53-1).
* The runner and validator command lines are Enaction's and the game's to
  define. Until package B2 swaps the stubs for the real binaries, the
  pipeline is tested against stub binaries only.

== Open questions for reconciliation

* The validator's command line and fault format belong to package A2. The
  adapter reads a fault as one JSON object `{"rule", "path"}` or
  `{"faults": [{"rule", "path"}, ...]}` on stdout or stderr.
* How the runner emits two documents is not fixed by the route. The adapter
  reads one JSON document per line of stdout and passes the whole stream to
  the validator.

== Amendment 2026-11-14 (package B2): one file per document

Status: Accepted (owner ruling, 2026-11-19), with the decision it amends.

The real binaries now exist and differ from the readings above, which were
made from contract prose against stubs:

* `idaptik-weevil-replay --profile P --ticks N --seed S --emit-epistemic PATH
  [--emit-mind-trace PATH]` writes each document to its own file. Its stdout
  is a human summary that ends with `wrote PATH` for each file;
* `enaction-validate --policies FILE [--mind-trace FILE] < runner-output.json`
  needs the caller's policies, reads the mind trace from a file, prints the
  canonical envelope and then the canonical mind trace on exit 0, and on exit
  1 prints exactly one canonical line `{"faults":[{"detail","path","rule"}]}`
  on stdout (CAC-KERNEL section 9).

So the decision changes as follows; the rest stands:

. the runner's arguments are a caller-supplied template in which the whole
  arguments `{runner_output}` and `{mind_trace}` name files that the adapter
  chooses inside one private temporary directory, one subdirectory per run;
. replay identity compares the bytes of each document pair, under a size cap
  per file. It no longer compares runner stdout, because the real runner
  prints its output paths there and those differ between the two runs;
. the validator receives `--policies` (required), `--mind-trace` when a mind
  trace was asked for, the runner output on stdin, and any extra arguments;
. a refusal is read from stdout only, in the canonical form only. The bare
  `{"rule","path"}` object and the stderr fallback of the first version are
  gone, because the real validator prints neither;
. the response document becomes `ums-enaction-preview-response/2`.

The open questions above are answered: the fault format is CAC-KERNEL
section 9's, and the runner emits one file per document.
